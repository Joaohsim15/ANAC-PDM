Batch, streaming e deploy do modelo

Predição de atraso de voos com meteorologia em streaming

O histórico de voos é processado em batch e treina o modelo. Observações meteorológicas dos aeroportos entram em tempo real por Pub/Sub e Dataflow. O modelo é servido por uma API no Cloud Run, que consulta o endpoint do Vertex AI.

Motivação

O modelo do T1 só via o voo, mas o clima também atrasa voos

No T1 o modelo usava apenas dados do voo: companhia, rota, aeronave, horário e calendário, e o desempenho ficou abaixo do esperado. Faltava uma causa conhecida de atraso: as condições do clima no aeroporto de origem.

Com as variáveis de clima, o modelo teve uma pequena melhora. O ganho é limitado porque trovoada e chuva aparecem em menos de 9% dos voos; nos demais, o clima não traz informação nova. Fenômenos como trovoada passaram a figurar entre as 6 variáveis de maior peso do modelo.

Arquitetura de ponta a ponta

Dois pipelines que se encontram no modelo

Batch Histórico e treino

Voos chegam uma vez por mês. O batch organiza 9 anos de voos e clima em camadas, junta a observação de cada voo e treina o modelo.

Streaming Condição atual

O clima muda a cada hora. O streaming recebe cada observação nova, valida e grava no mesmo dataset do histórico, com o mesmo contrato de campos.

A2 Pipeline de ingestão

Pub/Sub → Dataflow → BigQuery, com dead-letter

Pub/Sub
  • Tópico anac-metar, retenção de 1 dia.
  • Assinatura pull lida pelo Dataflow.
Dataflow
  • Apache Beam em modo streaming, Streaming Engine.
  • 1 a 2 workers e2-standard-2.
  • Valida tipo, faixa e domínio pelo contrato.
BigQuery e dead-letter
  • Streaming inserts, partição diária, cluster por aeroporto.
  • Inválidas vão para anac-metar-dlq com o motivo.

O dead-letter é feito dentro do pipeline. Campos fora do contrato são recusados, o que impede que um dado posterior à partida chegue à tabela.

  • Dataflow em vez de um script: escala sozinho, não perde mensagem se cair e separa o que é inválido.
  • Gravação contínua no BigQuery: cada observação fica consultável em segundos.
  • Batch em SQL no próprio BigQuery: o histórico é grande, mas muda só uma vez por mês.

Exemplo medido: buscar os voos de um aeroporto em um mês lê 1,1 MB. Sem a partição por dia, a mesma consulta lê 37 MB.

Parte B

Arquitetura de deploy da API do modelo

Como o modelo treinado no BigQuery ML chega a um endpoint, e como a API no Cloud Run atende uma requisição.

B1 Do treino ao endpoint

O modelo vai do BigQuery ML ao Vertex AI sem exportar arquivo

Registro do modelo
  • MODEL_REGISTRY = 'VERTEX_AI' no próprio CREATE MODEL.
  • O endpoint serve o modelo vigente no BigQuery, sem cópia.
Imagem da API
  • python:3.12-slim, usuário sem privilégio.
  • Leva o contrato junto: API e modelo não divergem.
Cloud Run
  • 1 vCPU, 512 MiB, até 3 instâncias.
  • Escala a zero fora da demo; 1 instância quente na apresentação.
  • Sem acesso anônimo.
B2 Caminho de uma requisição

Da chamada à probabilidade de atraso

  1. Pedido

    O sistema envia os dados do voo e o clima no aeroporto de origem.

  2. Validação

    A API confere quem chamou e se os dados seguem o contrato. O que estiver fora é recusado.

  3. Modelo

    A API consulta o modelo implantado no Vertex AI.

  4. Resposta

    Volta a probabilidade de o voo atrasar, e a previsão fica registrada para comparar com o que aconteceu.
